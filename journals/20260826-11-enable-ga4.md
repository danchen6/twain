# Enable production GA4 behind the existing consent boundary

> Immutable episodic record. Do not edit; supersede with a newer journal.

## Context

The consent-gated Google Analytics 4 adapter had shipped disabled while awaiting a production web-stream identifier. Dan supplied `G-BBJX7TJD6W` and explicitly requested repository enablement plus a commit. The prior consent notice already named Google Analytics, disclosed the outcome and standard-context data boundary, and recorded that filling the disclosed stream ID would not itself require a new consent version.

Repository access cannot establish the GA account's data-retention, Google/privacy, custom-definition, key-event, or jurisdiction-specific settings. Those external controls remain an explicit account-side rollout boundary rather than being inferred as complete.

## Decision process

- Enable the existing native adapter with the supplied stream and keep `debug: false`; do not paste Google's static snippet into `index.html`, because that would bypass the established no-request-before-consent contract.
- Preserve `twain:analytics-consent:v1`. The vendor, purpose, event schema, and disclosed standard context did not change, so re-prompting solely for the stream identifier would contradict the earlier consent-version decision. Browsers that previously granted the disclosed future GA collection may therefore initialize the tag after this configuration deploys.
- Lock the exact production stream and debug-off setting in the Node suite. Keep separate fake-client coverage for disabled, invalid, undecided, granted, and revoked configurations.
- Change rendered QA from proving a permanently disabled adapter to proving the production behavior: undecided and declined pages are tag- and request-free, a grant initializes only the approved stream, and active withdrawal reloads into a clean tag-free page.
- Intercept and locally fulfill Google endpoints inside the QA browser. Sending harness traffic to the real property would pollute production data and make the quality gate network-dependent.

Rejected alternatives were adding Google Tag Manager, introducing build-time environment injection, embedding a static tag, sending real QA traffic, or bumping consent storage. They add unnecessary infrastructure, weaken the consent boundary, contaminate analytics, or imply a material consent change that did not occur.

## Outcome

- `ANALYTICS_CONFIG` now enables `G-BBJX7TJD6W` with debug mode off.
- The Google tag remains absent from static HTML and unreachable until a valid browser-local `granted` record exists. Declining or leaving the choice undecided creates no tag, `dataLayer`, or Google request; revoking an active grant reloads into the same tag-free state.
- Unit and rendered-browser coverage now lock the production configuration and consent/network boundary without contacting GA.
- README, product, architecture, analytics, quality, visual-QA procedure, and backlog memory now describe the enabled repository state and distinguish it from unverified account-side rollout work.

## Trade-offs and consequences

- The Measurement ID is intentionally public in the static client; it is a destination identifier, not an account credential.
- Previously granted v1 choices begin collection after deployment without another prompt, consistent with their disclosed vendor and purpose. Clearing site data, changing browsers, or using private browsing still creates a separate choice.
- Consented analytics remains a self-selected sample and must not be represented as whole-audience behavior.
- GA Console configuration and end-to-end DebugView receipt are outside repository verification. The backlog retains these items, along with the broader decision about whether browser-local consent timestamps satisfy the intended audit requirements.

## Verification

- `npm test` passed with the production stream assertion and all existing generator, rule, persistence, static, analytics, and telemetry coverage.
- `npm run visual-qa -- --output /private/tmp/twain-visual-qa-ga4-enable` passed the complete five-stage browser harness in Microsoft Edge. The harness intercepted the approved tag request and sent no QA traffic to GA.
- The browser run proved no pre-consent or declined tag, `dataLayer`, or request; grant-only initialization of `G-BBJX7TJD6W` with Google Signals and ad personalization disabled; persisted grant; and a tag-free reload after active withdrawal.
- Privacy banner captures were inspected at 1440×1000, 768×1024, 390×844, and 320×800, plus the details dialog at 390×844. All remained contained, legible, and visually consistent; no defect or recapture was required.
- `node --check src/analytics.js`, `node --check .agents/skills/visual-qa/scripts/run.mjs`, and `git diff --check` passed.
